Sagittal MSM

A multi-scalar multiplication algorithm for zero-knowledge provers, invented by Karl Preisner in 2022 and built for GPUs at Sindri Labs in 2023. This page explains it from the ground up, with step-by-step animations.

Source on GitHub Full docs

On BLS12-377 at 220 points, with the proving key precomputed once and reused across proofs, Sagittal ran an MSM in 64 ms: 1.7× faster than every ZPrize 2022 GPU entry that runs on a V100, and faster than all entries but one (Yrrid, 48 ms) on an A10G.

1. MSM and elliptic-curve arithmetic

A dot product

A dot product multiplies two lists pairwise and adds up the results. A multi-scalar multiplication (MSM) has the same shape, except the second list holds elliptic-curve points instead of numbers. Step through both:

The scalars ki are ordinary integers, about 253 bits long. The points Pi are pairs (x, y) of 377-bit numbers. In a zero-knowledge prover the points are fixed (they come from the proving key and are the same for every proof of a circuit) and the scalars change every proof. Anything computed from the points alone can be computed once and reused.

Adding two points

The curves here have the equation y² = x³ + b (b = 1 for BLS12-377). Over the real numbers, adding two points has a picture: draw the line through P and Q, find where it meets the curve again, and reflect across the x-axis. Real curves use the same formulas with every number taken modulo a 377-bit prime.

λ  = (y₂ − y₁) / (x₂ − x₁)      for doubling: λ = 3x₁² / (2y₁)
x₃ = λ² − x₁ − x₂
y₃ = λ(x₁ − x₃) − y₁

Modulo p, dividing means multiplying by an inverse, which costs hundreds of multiplications. So implementations carry a running denominator in extra coordinates and divide once at the end. One addition then costs about 10–16 field multiplications: 10 for a mixed add (accumulator + stored point), 14 for a full add and 9 for a doubling, in XYZZ coordinates.

There is no multiply

A curve has only addition. "k·P" means adding P to itself k times. There is no way to multiply a point by a number directly, or to multiply two points, and recovering k from k·P (the discrete logarithm) is believed infeasible. That is what makes these curves useful for cryptography. Instead, double-and-add reads k's bits from the top: double at every bit, add P at every 1.

A 253-bit scalar takes about 252 doublings and 126 additions: 376 curve operations per point, measured. A naive MSM does that for every point, about 400 million curve operations at 220 points.

2. Big numbers and GPUs

Numbers bigger than a machine word

A machine word is the size of number a processor handles in one instruction: 64 bits on a CPU and 32 bits for a GPU's integer units. A 377-bit number is stored as 12 words of 32 bits, and multiplying two of them works like long multiplication on paper, one word pair at a time:

That is about 300 word multiply-adds per field multiplication (Montgomery multiplication, CIOS: 2s² + s for s = 12 words), and about 3,000 per curve addition. Sindri's GPU code stored values in Montgomery form, which lets the reduction mod p use multiplications instead of division.

GPU memory and threads

A GPU runs thousands of threads in groups of 32 called warps. A warp executes one instruction for all 32 threads together, so threads that need to do different things wait for each other. Memory comes in tiers:

RegistersUp to 255 × 32-bit per thread. One XYZZ accumulator alone takes 48.
Shared memory48 KB per block by default, on-chip. Holds one Sagittal table for g ≤ 9.
Global memory16–48 GB, hundreds of cycles away. Points, scalars and precomputed tables.
Host memoryAcross PCIe. Where Sagittal combines its 253 buckets.

Why data-dependent work is costly

In Pippenger's bucket method the bucket a point goes to depends on its scalar, so many threads can target the same bucket at once. A bucket update is a curve addition (about 3,000 multiply-adds), not one instruction, so the GPU's atomic add can't do it: threads must take turns, or the points must be sorted by bucket first. Fast implementations avoid the collisions by sorting points by bucket and balancing bucket sizes, and the ZPrize winners do that very well. But it is extra work every proof. An algorithm whose work is fixed in advance doesn't pay it.

3. Pippenger's bucket method

Every fast MSM builds on this. Write each scalar in base 2c: c-bit digits called windows. In each window every point goes into the bucket for its digit. Then a running sum from the top bucket down computes Σ d·bucket[d] with about two additions per bucket, and windows are combined by doubling c times between them. Step through 8 scalars with c = 4:

The best window grows with n: c = 17 at 220 points, which means 15 windows × 65,536 buckets ≈ 983,000 buckets, filled by the data. The ZPrize 2022 winners (Yrrid and MatterLabs) also precompute shifted copies of every point so all windows fold into a few bucket sets.

4. Sagittal MSM

Pippenger cuts the scalar bit matrix into strips c bits wide and n rows tall. Sagittal cuts it into blocks 1 bit wide and g rows tall. A block's g bits select one subset sum of its batch's points. That sum depends only on the points, so every subset sum is precomputed once per proving key.

Step 1, once per proving key: build the tables

Each batch of g points gets its own table holding every combination (not permutation: P1 + P2 = P2 + P1) of its points: 2g − 1 entries, each built with one addition from two entries built earlier. Here, 8 points in batches of g = 4 need 2 tables:

Step 2, every proof: look up and add

For each batch and each bit, the g scalar bits form a pattern that picks one table entry, added to the bucket for that bit. There is one bucket per scalar bit. The bit patterns match the table above: 0101 is P2 + P4 in both.

Finally the b buckets are combined with Horner's rule, b − 1 doublings in total (about 500 operations for 253-bit scalars, whatever n is). There is no bucket reduction, every bucket gets exactly one lookup per batch, and every addition is the cheap mixed kind.

One batch on its own is Straus's method (Shamir's trick). What Sagittal adds is the bit-major slicing, offline tables over a fixed proving key, and a schedule fixed before any scalar is read.

5. Why Sagittal suits GPUs

At 220 points Sagittal does more curve operations than a tuned Pippenger. It still ran faster on GPUs in 2023, because of the shape of its work:

  • Thread = bit, block = batch. Every thread does one lookup and one addition per batch, so warps don't diverge.
  • Tables in shared memory. A batch's 2g entries of 96 bytes fit in 48 KB for g ≤ 9.
  • A fixed order. The fastest kernel spreads blocks over 256 copies of the buckets by block number, not by the data, and the 253 final buckets are combined on the CPU.

The catch is memory. Tables hold (2g − 1)/g points per input point, so large MSMs force small g. On a 16 GiB V100 the largest g that fits is 8 at 222 and 5 at 224, exactly what the 2023 runs used.

Against the Yrrid configuration on the same A10G, Sagittal does 1.87× more curve operations and 1.45× more field multiplications, but was only 1.33× slower (64 vs 48 ms). Field cost explains most of the gap; the shape of the work explains the rest.

Precompute is cheap. Sagittal's tables cost 385 field multiplications per point to build, about 5× less than the Yrrid configuration's shifted points (2,110). For a single proof, Sagittal costs 743 per point against 2,357; the Yrrid configuration pulls ahead only above 16 proofs per proving key.

7. How the numbers are made

The repository is a Python reference implementation that counts every operation. Algorithms only call group operations inside named phases, and the group counts them, so the counts always describe the code that ran. They run on BN254, BLS12-377 and a 64-bit Goldilocks test curve (in Jacobian or XYZZ coordinates, with field operations counted too), and on a fast counting group with the same structure. A closed-form model, tested against measured counts within 2%, extends the comparison to 224 points.

The animations above use small examples (8 points, 4–8-bit scalars) so every step fits on screen. Every number on this page comes from benchmarks/results/ or the 2023 GPU logs, and the methodology page lists what they don't cover.
